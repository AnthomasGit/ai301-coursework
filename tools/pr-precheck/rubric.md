# Rubric: is this pull request ready to submit?

Each check reads the PR itself against the plan, the issue, and the repo's stated asks, never the write-up's polish. Run the checks in table order. Where a cell says "the plan", read the plan context in eval mode and `plan.md` in live mode, deviation notes included.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's list of changed files and each hunk, read against the plan's `Files:` list, its scope and not-in-scope lines, and any deviation or deferral notes | Passes if all three hold. (1) Every changed file is named by the plan: the file itself, its folder, or a description that picks out exactly that file ("a changelog entry", "the i18n english set", "unit test for the aggregation"), or a deviation note names it. (2) No hunk adds something the plan scopes out (a new option, setting, flag, or rename) or rewrites code the plan does not target. (3) Every change the plan promises is in the diff, unless a deferral note in the plan or the description names the missing part. An honestly recorded deferral passes. A file or hunk with no plan line and no note behind it fails. | required |
| claims-match-diff | Every concrete claim in the title, description, and checklist, read against the diff. Concrete claims include "implements the plan exactly / no changes beyond it", tests or fixtures added for named cases, files added (changelog, docs), and "no X added" | Passes if a diff line bears out every concrete claim. A claim that something was not added passes when no hunk adds it. A claim of tests for N named cases needs each case's input to be exercised somewhere in the added tests or fixtures. A case covered by an assertion inside a shared test counts; one test function can cover several cases. A fidelity claim ("exactly as planned", "no changes beyond the plan") fails whenever the diff holds a file or hunk that plan-fidelity's conditions (1) or (2) would fail. The check fails in either direction: the description claims something the diff does not deliver, or the diff carries something the description says it does not. | required |
| repro-evidence | The test-evidence section (live: `test_evidence.md`), read against the plan's test plan and the repro's failing step | Passes if all three hold. (1) The repro's failing step is re-run on the branch, with a before and an after. Every other failure mode the plan's test plan says the fix addresses is covered by at least an after, which may be one sentence naming the observed result. A failure mode the evidence never mentions fails this condition. A mode the plan or description explicitly defers is exempt. (2) Each after states the observed result itself: the printed output, the value, the error text, the exit code, or the absence of the named before-error. A short description of that result (in a comment line, for example) counts. A verdict alone does not count: "works", "fixed", "matches the expected output byte for byte", "verified on my machine". (3) The run exercises the path the diff changes, not only a control or an unchanged path. | required |
| clean-diff | Every hunk in the diff | Passes if no hunk carries debris: a debug print or log line, a commented-out code block or earlier attempt, a dead or unused function, a TODO left on the change, whitespace, re-indent, or import churn, or a refactor or restyle of code unrelated to the fix. A change the fix itself needs (a new import it uses, a test fixture) is not debris. | required |
| repo-asks | The repo's stated asks for PRs (eval: the repo-facts block's pull-request and contribution-policy lines; live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the description and the diff | Passes if every mandatory ask that applies to a PR is met with real content: each required template section is filled, each required checklist item is answered, the issue is linked in the form asked for (for example `closes #N` or `fixes #N`), and each required artifact is in the diff (for example a changelog or whatsnew entry). A checklist item answered "n/a" with a reason that is true of the diff passes. If the stated policy requires disclosure of AI use, treat the PR as AI-assisted: the description must disclose it as the policy asks (for example the tool and the extent). If the repo states no asks, the check passes. | required |
| checks-shown | The test-evidence section's control runs and repo-suite runs, and the commit list | Passes if every control the plan's test plan names, and the repo's own test suite or checks, are shown as a command plus its printed output or result line, and every commit message says what that commit changes. A sentence or a `#` note claiming something passed or stayed unchanged is not output. A placeholder commit message ("wip", "fix", "misc cleanups") fails. | preferred |
| thread-fit | The description, read against the thread highlights | Passes if the description engages any explicit maintainer direction, question, or decision in the thread (building on it, answering it, or citing it for a deferral) and reads as a response to this issue. If the thread holds no such direction, it passes. | preferred |

## Verdict rule

Accept (ready to submit) if every required check passes. Any required check that grades fail or unclear holds the package (reject): an unclear required check is a claim the package does not let you verify, so it counts as fail. Preferred checks never change the verdict. Report their fails and unclears in the summary as fixes to make before submitting. The deciding check quoted with the verdict is the first required check, in table order, that did not pass. For an accept, quote the repro-evidence check's evidence.

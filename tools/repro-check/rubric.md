# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The `Environment:` line of the candidate repro report (plus any environment mention in the claim comment), read against the issue's environment and **Repo facts** → latest release (Environment family in `references/evidence-guide.md`). | The report names the OS and the tool under test with its version and where it came from (package manager, release binary, source, hosted playground). It does NOT have to match the issue: a different OS, a newer release, or a different install method passes as long as every version or platform difference from what the issue states is named outright in the package (for example "issue filed on 3.8.4; this is 3.9.6", "on a different OS"). When the issue states no version, a current release needs no statement. Fails if there is no environment record, the OS or tool version is missing, or the tool version is older than / a different build channel from the issue's without the package saying so. | required |
| Faithful, followable steps | The steps and commands in the candidate repro report, read against the issue's steps, trigger input, and starting-state conditions (Steps family). | A stranger could re-run the steps from nothing: every input the trigger needs is shown, built in the steps, or described precisely enough to rebuild (for example "a minimal env.yml with a valid dependencies list plus a `category:` section", or "the issue's two inputs, verbatim"). Fails on private repos, unshared configs, or inputs that cannot be reconstructed from the package plus the issue. The trigger is the issue's: same command or API call on the same kind of input. A minimal re-creation passes when it keeps every condition the issue names as triggering (for example a local file instead of the issue's URL, an `--offline` flag that prints the same request, a fresh playground with the issue's exact code). Fails when the input or command is changed in a way that sends it down a different path (different syntax, an altered expression, a different range form, skipping the UI the issue used) or when steps are absent. | required |
| Behavior shown | The literal output blocks in the candidate repro report, read against the issue's stated symptom and any output the issue quotes (Behavior shown family). | EITHER (a) reproduced: output that appears in the report, produced by the steps, shows the issue's specific failure (same error kind, same wrong value, same crash vs graceful exit), with any quoted output matching apart from local paths, timestamps, and generated ids/hashes; OR (b) honest cannot-reproduce: the report says plainly it could not reproduce, shows the output of a faithful attempt, and names what differed from the issue's conditions. Fails when the output is a different error or a nearby symptom, when the output shows only that the tool runs, or when the behavior is only described in prose with no artifact. | required |
| Claims backed, no promises | Every claim in the candidate claim comment and the report's `Actual:` line and conclusions (Honesty family). | The central claim traces to an artifact: "reproduced" only where Behavior shown passes (a); generalizations only as far as the runs go (another release, platform, or build is only claimed if it was run). Root causes are either shown or offered as a hedged hypothesis ("likely", "my guess", "may be required"); asserting a cause as verified with nothing shown fails. Supporting remarks (a control run or extra attempt described in prose alongside a shown main artifact) do not fail this check. No fix dates, "guaranteed", or "fix coming" promises. Fails on any central claim, generalization, verified-cause assertion, or promise the package does not back. | required |
| Specific claim comment | The candidate claim comment, read against the issue (Comms family). | The claim names this issue's specific behavior and a concrete next step tied to the code, output, or thread (for example a file, function, or pointer from the thread). Fails if it is interchangeable boilerplate ("assign me", "keep it reserved", praise with nothing issue-specific), or a +1 with no intent. | required |
| AI disclosure when required | **Repo facts** → contribution policy, read against the claim comment and repro report (Disclosure family). | Treat every package as AI-assisted work. If the policy requires disclosing AI use in issue comments or in any contribution "in any form", the comments must disclose the tool and the extent of assistance. Passes automatically when the policy has no disclosure requirement, only requires disclosure in pull requests, or only asks that comments be human-written in the contributor's own words. | required |
| Thread and template awareness | **Thread highlights** and **Repo facts** → bug-report template, read against the claim and report. | The claim acknowledges any competing fix or claim in the thread, and the report covers the fields the bug template asks for. | preferred |

## Verdict rule

Accept (ready to post) only if every required check passes. Any
required check graded `fail` or `unclear` makes the verdict reject
(hold): proof that cannot be verified is not ready to post. Preferred
checks never change the verdict.
